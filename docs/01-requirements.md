# 01 需求：用户、目标、范围与成功标准

## 用户与场景

内容运营团队每天需要把一批待发布的视频素材排进各渠道的发布时段。人工做这件事要反复确认三件事：素材能不能发（审核）、要求的时段是否空闲（冲突）、改了时间有没有告诉需求方（确认）。本 Agent 帮运营完成审核与排期的“草稿”环节，最终是否发布仍由人决定。

## 目标

输入一批素材及其发布时间要求，对每个素材输出：

| 输出项 | 说明 |
|---|---|
| 审核状态 | approved / needs_info / blocked / needs_verification / not_checked |
| 风险原因 | 命中的审核规则及说明 |
| 建议时段 | 与要求一致或替代时段 |
| 待确认项 | 改动用户要求时必须列出，等待用户确认 |
| 草稿保存状态 | 是否保存、草稿 ID、created / updated / deduplicated / failed |
| 任务状态 | completed / needs_user_action / partial_failed / incomplete |

## 输入与材料（全部为合成数据）

- 请求：`request_id` 与素材列表，每项包含 `material_id`、`channel`、`date`、`preferred_time`、`time_flexibility`（flexible 可建议替代时段，fixed 不得擅自改）。
- `data/materials.json`：6 个素材，覆盖完整、缺字段、音乐授权未知、含极限词等情况。
- `data/rules.json`：必填字段、广告法极限词、背景音乐授权、渠道时长上限 4 条规则。
- `data/schedule.json`：每天 6 个时段，已有 18:00、21:00 被占用。
- `data/license_db.json`：版权库，供补查。

## 范围

做：审核、补查、时段查询、替代时段建议、草稿保存（幂等）、用户确认草稿、故障注入、步数上限、运行记录、自动核对。

不做：真实发布（系统中不存在发布接口）、界面、线上部署、多 Agent、跨日期改期、多渠道联动排期。

## 业务边界（必须遵守）

1. **只存草稿，不发布**：没有发布工具；输出 `published` 恒为 false；任何“已发布”表述会被更正。
2. **确认边界**：建议时段与用户要求不同 → 必须标记待确认；`fixed` 时段与日期、渠道为硬性要求，Agent 无权修改。
3. **不虚报**：草稿保存状态以工具真实返回为准。
4. **无冲突**：草稿不能落在已占用时段，也不能与其他素材的草稿重叠。
5. **防重复**：同一素材、同一渠道、同一天只有一份草稿；重复提交相同内容不新建。

## 必须验收点与成功标准

| 验收点 | 成功标准 | 用例 |
|---|---|---|
| 正常排期 | 审核通过、要求时段空闲 → 保存草稿，任务 completed | case01、case05、case09、case12 |
| 素材信息缺失 | 列出缺失字段，不保存草稿，状态 needs_info | case03 |
| 规则风险 | 需补查则先补查；阻断时不保存并说明原因；补查通过可继续排期 | case04、case05、case12 |
| 时段冲突 | 选替代空闲时段并标记待确认；fixed 时段不擅自改 | case02、case07、case10、case12 |
| 重复提交 | 相同请求重复运行只有一份草稿；占用变化后重提，更新同一份草稿 | case06、case07 |
| 保存失败 | 明确返回失败，不虚报成功，存储中无草稿 | case08 |
| （通用）工具失败 | 可重试错误重试后继续 | case09 |
| （通用）执行上限 | 达到上限返回 incomplete 及原因 | case11 |

所有用例额外检查三条不变量：从未发布、草稿无时段冲突、报告的保存状态与存储一致。
