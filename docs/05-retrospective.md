# 05 复盘：最难的问题、学习收获、下一步

## 最难的问题：理解题目

对我来说，最难的不是写代码，而是读懂题目到底要什么。主要卡在两个地方。

### 1. “重复提交”到底指什么

题目要求“相同请求重复保存只产生一份草稿”，审核要点里又说要“更换占用时段并重复提交”。一开始我不明白：这是指用户连点了两次保存，还是同一个请求跑两遍？“更换占用时段并重复提交”又是什么场景？

后来对照 case06 和 case07 的真实运行记录才理解，这是同一个请求再提交一次的两种情况：

- **时段没变（case06）**：第二次运行时，模型查到 19:00 是 M01 自己的草稿，于是仍保存 19:00，系统返回 `deduplicated`，存储里还是只有一份 v1。
- **时段被别人占了（case07）**：第二次运行前 19:00 被 M92 占用，模型改选 20:00，系统在原来那份草稿上 `updated` 成 v2。草稿 ID 不变，仍然只有一份。

所以“防重复”的意思不是“拒绝第二次提交”，而是**无论提交多少次，一个素材在同一天同一渠道始终只有一份草稿**；内容没变就不动，内容变了就改原来那份。

### 2. 什么是“硬性发布要求”和“确认边界”

题目说“未经用户同意不得擅自改变硬性发布要求”。我一开始分不清：哪些能改、哪些不能改？“建议 19:00 并标记待确认”和“直接改成 19:00”有什么区别？

后来理解为：

- **不能改的**：日期、渠道，以及标为 `fixed` 的时间。case10 里 M02 要求固定 18:00，但 18:00 被占了，模型就没有保存草稿，只给出建议并请用户决定。
- **可以建议换、但要用户确认的**：标为 `flexible` 的时间。case02 里模型保存了 19:00 的草稿，但状态是“待确认”，而不是直接替用户做决定。
- **任何时候都不能越过的**：只能存草稿，不能说“已发布”。

“建议并待确认”和“直接改”的区别在于：**最终拍板的人是用户还是 Agent**。确认边界就是 Agent 能自己做主的范围。

## 学习收获

### 对 Agent / ReAct 循环的理解：决策交给模型，底线交给代码

以前我以为“智能”的程序就是写很多 if/else。做完这个项目，我理解 ReAct 循环是这样的：模型选择调用哪个工具 → 程序执行 → 把结果交回模型 → 模型根据结果决定下一步，循环直到完成。下一步做什么，不是代码写死的，而是模型看到工具返回后自己判断的。

但模型不是 100% 可靠。所以这个项目的分工是：

- **灵活的决策交给模型**：先排哪个素材、换到哪个时段、要不要补查、要不要重试。`prompts.py` 里只写了目标、边界和“遇到什么情况可以怎么办”，没有规定调用顺序。
- **不能出错的底线交给代码**：不能发布、不能改硬性要求、不能冲突、不能虚报保存成功。这些由工具层和对账层强制保证，模型就算判断错了也写不进去。
- **防重复由存储层保证**：在 `store.py` 里，用“素材 + 渠道 + 日期”作为唯一键，保证同一个组合只有一份草稿。

### 让我意外的地方：模型自己决定了排期顺序

最让我意外的是 case12。4 个素材一起排期，提示词里并没有规定先排谁，但模型自己做了一个合理的安排：先给原定时段空闲的 M05（19:00）和 M02（20:00）保存草稿，再给 18:00 被占用的 M01 找替代时段。此时 19:00 和 20:00 已经分配出去了，它就选了 12:00，并在确认事项里主动解释：“19:00、20:00 已分配给 M05、M02，故未选更接近的时段”。

这让我真正看到了“模型根据工具结果调整动作”是什么样子：同样的代码，因为前面的保存改变了时段占用，后面的选择也跟着变了。这种顺序如果用 if/else 写死，很难覆盖所有组合。

## 下一步：验证稳定性

如果再给我一天，我最想做的是**每个用例多跑几次，看结果是否稳定**。

现在的 12/12 通过来自每个用例只跑 1 次。模型的输出有随机性，即使 temperature 设为 0 也不保证每次都一样。比如 case10 里模型第一次提交的 JSON 格式就出错了，只是下一轮自己改对了。如果哪次没改对，或者在步数上限更紧的情况下，结果可能就不一样。

具体做法：每个用例跑 5～10 次，统计每个用例的通过率，找出最容易出错的决策点（比如替代时段选得对不对、会不会忘记标待确认），再针对性地改提示词或工具描述，然后再跑一轮对比。

其他可以继续改进的地方：

1. 减少多余调用：在提示词里说明“审核不通过时无需查询时段”。
2. 让模型自己修正错误：现在 Guard 只是事后更正最终结果，可以改成把差异告诉模型，让它重新处理。
3. 支持跨天改期：现在只在同一天里找替代时段，当天排满时只能请用户决定。
